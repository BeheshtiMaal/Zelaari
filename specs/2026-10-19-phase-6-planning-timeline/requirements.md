# Phase 6: Planning and activity timeline. Requirements

Status: **Approved by the user; implementation in progress.**

## Goal
Analyze before making changes, submit a reviewable plan, enforce its boundaries in the engine, and show the real parent/delegated activity in a durable step-based timeline. The human can steer and stop the original run.

## References
- `AGENTS.md`, `prompts/00-kickoff.md`, `prompts/phase-06-planning-timeline.md` and the four constitution files.
- Visual source: `docs/mock-source/Run.dc.html`, `Main.dc.html`, `docs/design-tokens.md`. Existing Settings chrome supplies the narrowly scoped planning-controls location; its undrawn inner controls use the existing form tokens.
- Phase 5 validation/handoff: durable mixed human barrier, exact interrupt/call identity, independent decisions, checkpoint-before-publication, vault/provider reconstruction, explicit Stop, trusted OpenUI question controls and no replay of uncertain effects.
- Phase 1 requirements/plan/validation provide the document format.

## In scope
`submit_plan`, `write_todos` progress integration, initial/deviation gates and their settings, durable plan revisions and scoped events, trusted PlanChecklist, the Run/Main activity timeline, real provider reasoning, concurrent read-only reviewer/researcher delegates, actual summarization notices, right-panel telemetry, mid-run steering, cancellation/recovery, offline fixtures and Windows fa/en verification.

## Out of scope
Phase 7 test discovery, verify/fix loop, fix budgets, context breakdown/ring interactions and new compaction policy; Phase 8 skills, connectors and web-search backend; scheduler, installer delivery and unrelated settings. Instrument actual installed summarization behavior now; configuring the Phase 7 compaction policy remains deferred. Display unavailable telemetry honestly instead of inventing mock numbers.

## Requirements
- **R1 — Structured plans and analysis first.** `submit_plan` accepts a bounded nonempty ordered list of steps with stable unique IDs, nonblank titles, optional expected workspace-relative file globs, optional verify command and a high-risk declaration. Establish/test exact bounds and installed tool contracts in Step 1. Safe project reads, questions and final read-only answers need no artificial plan; new file mutations and commands require an accepted plan and an active step before dispatch. A verification command in the plan is descriptive, never executed by submitting or approving the plan. Prompt rules instruct analysis/read-before-edit, small steps, following the plan and reporting deviations; enforcement does not depend on those instructions. Existing `/grill` readiness remains a prerequisite before implementation.
- **R2 — Initial gate.** Outside Auto (Ask and Read-only), require explicit approval when steps >= the configured step threshold (default 4), unique expected files > the configured file threshold (default 3), or any step is high-risk. Smaller plans are adopted and shown immediately; Auto skips only this initial gate. Read-only may plan but never gains mutation/command access. High-risk status includes the supplied flag and risk identified from a declared verify command by the existing classifier; the fixed high-risk trigger has no disable switch outside Auto. Plan approval is separate from each tool's permission/risk/jail checks.
- **R3 — File counting and settings.** At review, deduplicate jailed concrete targets across steps: expand existing-file matches and count literal new-file paths, without counting one glob as one file. Broad/unknown expansions that cannot establish a bounded small count require review outside Auto; expose known/uncertain counts honestly. Bind the reviewed plan to the effective settings and file-scope revision and revalidate before adoption. Expose validated step/file thresholds and a default-on deviation toggle in Settings > Permissions for the selected workspace. Store planning fields in `.harness/config.json`, preserving unrelated keys; malformed files must not be overwritten. Changes to this protected engine file use a durable configuration approval in every mode, with preview/revision, reject/stale behavior and snapshot protection. The high-risk trigger remains fixed. Step 1 specifies positive finite integer bounds and exact threshold semantics.
- **R4 — Durable plan decisions.** Initial and deviation reviews use the shared approval surface/inbox and existing human barrier. Reviews show the actual ordered plan, declared targets/verify command, gate reason and a real revision diff for changes. Approve, reject with reason and edited-plan preview must validate the current plan/configuration and exact IDs; an edited plan is not silently adopted from unchecked JSON. Rejection retains the prior accepted scope and returns a readable result to the model. Initial rejection authorizes no implementation. Partial plan/tool/question decisions survive restart, and every required request resolves before sibling tools can execute. Acceptance of a plan in one turn cannot retroactively authorize an unclassified sibling effect.
- **R5 — Deviation gate.** With the toggle enabled, both Ask and Auto require approval before mutating outside accepted declared globs, dropping an accepted step, or adding more than two steps. Apply this before dispatch and show the proposed scope/plan diff; approval adopts only that reviewed revision. Count added stable step IDs cumulatively against the last explicitly reviewed baseline (or original automatically adopted plan), so repeated one-step additions cannot evade the threshold. Reordering/renaming with preserved IDs cannot hide removed scope or a changed risk/verify command; material scope widening/replacement requires refreshed review. Empty/omitted globs grant no file scope. Any disabled deviation gate still leaves plan presence, mode, ordinary permissions, protected paths, jail and effect journals enforced. Commands with unenumerable file effects remain subject to command permissions; do not claim an OS sandbox or infer their entire write set from shell text.
- **R6 — Progress identity and state.** Continue using the installed `write_todos` tool for progress, with a verified adapter to accepted stable step IDs. Validate pending/in-progress/completed/failed transitions, retain completed history and refuse ambiguous identity mappings or silent plan replacement. Publish `plan.created` for adopted plans and `plan.step.updated` for real transitions. Allow one active parent step; concurrent delegates attach to that parent by ID. A step cannot be finalized while its child activities remain running. Model-written todo edits that alter plan structure must pass R5 rather than bypass it. Keep pre-plan analysis/unscoped legacy events in an honest analysis/history group instead of inventing a submitted plan.
- **R7 — Typed activity and replay.** Extend generated protocol models for plan revision/gate state, step lifecycle, parent/delegate identity, timestamps, scoped tool/reasoning activity, summarization and steering. Preserve existing event types/clients through optional scope fields or explicit compatible records. Within each scope, start precedes deltas/actions and finish follows them; parallel delegates may interleave under one monotonically increasing run sequence. Do not flatten a child finish into a parent run finish. Persist state before announcement; reconcile stable event identities on reconstruction without duplicate publication. Replay/SSE reconnect must reproduce the timeline, plan, waiting state and results.
- **R8 — PlanChecklist.** Register a Zod-defined OpenUI PlanChecklist and share its trusted implementation between timeline and right-panel plan views. Model-composed controls can reference only the active run's engine-owned plan/revision; they cannot manufacture accepted scope, progress or approval. Show ordered statuses, real completion progress and pending/approved/rejected/automatic adoption state. Keep automatic adoption distinct from human approval. Existing ApprovalCard/DiffView/QuestionCard remain the decision components, including valid new in-plan/step metadata; no fabricated plan chips.
- **R9 — Run/Main timeline.** Match Run's inset shell/header, status chip, elapsed time/token usage, Stop, collapsed finished rows, active teal-bordered step, nested Thinking/delegates and inline amber approval. Match Main's expanded plan/diff and docked questions using the same state and components rather than parallel mock data. Finished steps default to a compact summary with actual duration, read/write/command counts and reasoning note; active step starts expanded. User expansion choices survive unrelated deltas/polling and navigation in a session. A step ending auto-collapses its Thinking panel once; manual re-expansion remains usable. Pending/failed/stopped/interrupted states and old run history remain readable. Durations derive from persisted start/end timestamps; elapsed wall time includes waiting and downtime, never fabricated replay timing.
- **R10 — Real Thinking.** Scope `reasoning.delta` to its actual model turn, step and delegate. Show only reasoning returned by the configured provider, with true provider/model attribution, streaming caret while receiving it and accessible collapse controls. Ordinary answer text and summaries never become reasoning. An active turn awaiting data is distinct from a completed turn with none; aggregate per-step reasoning availability and show `تفکر: این مدل استدلال ارسال نکرد` only when appropriate. Preserve text after completion/replay and prevent reasoning from one step/delegate leaking into another panel.
- **R11 — Read-only delegation.** Configure real reviewer and researcher sub-agents using verified installed Deep Agents APIs. Their tool layer enforces the parent workspace/worktree jail and a strict read-only ceiling regardless of Auto or permissive parent rules. No filesystem mutation, command execution, nested delegation, settings/permission changes, skills or implicit general-purpose agent may bypass this ceiling. Delegates expose only a verified safe-read allowlist; clarification needs return to the parent question barrier. Researcher uses available workspace/local documentation; network research is deferred with the web backend. Several delegates can execute concurrently. Publish real `subagent.started`/`subagent.finished` and scoped child activity with stable invocation identity, delegated task, status, result and duration. Render collapsible mini timelines and truthful read-only badges; errors, cancellation and interrupted recovery must be visible, without replaying uncertain effects.
- **R12 — Actual summarization.** Emit `context.summarized` only when the installed harness really summarizes/offloads conversation history, with verified operation/source and actual affected-message count where available. Instrument the actual state transition/hook; prose claiming a summary does not generate the event. Match Run's subdued notice and preserve the original event history for audit/replay. Tests may lower the library threshold to exercise the real path; no new production compaction setting or invented count is introduced. Redact summarizer input/output before checkpointing, including any model path that bypasses the ordinary call wrapper.
- **R13 — Right panel telemetry.** Match Run's 300px and Main's 288px information-panel hierarchy: plan, sub-agents, context bar, limits and current-task waiting count; Main's task-file section derives actual read/changed/pending target states from tool activity. Derive context usage from the latest actual request/estimate against the detected model context window, clearly marking estimates; cumulative billed run tokens are not current context occupancy. Show observed step activity and only configured/enforced cap or fix-attempt values actually available for that run. Unavailable limits/context data have a localized unavailable state with no fake `40`, `3`, `38%` or `0` values. Complete budget/fix counters and interactive context-ring breakdown remain Phase 7. Global badge counts approvals only; task dots/current-task waits retain Phase 5 question semantics.
- **R14 — Mid-run steering.** Implement authenticated `POST /runs/{id}/messages` with bounded nonblank text, client-generated submission identity and durable ordered acknowledgement. Keep the composer editable during a running/paused task; Enter submits a steering message, Shift+Enter adds a newline and its main action remains Stop during execution. Preserve the idle send flow and Phase 5 command-picker/question shortcuts. Show queued/delivered/error state; inject each accepted message once at the next safe parent-model boundary without starting a parallel graph invocation, cancelling current work or satisfying an approval/question. While paused, queue steering without releasing the barrier. Steering itself grants no permission: scope changes still require R5. Duplicate delivery, reconnect, restart, terminal runs and send/Stop races have defined tested outcomes; failed submission retains the draft.
- **R15 — Stop, recovery and privacy.** Acknowledge explicit Stop/emit terminal state within one second during reasoning, tools, a human barrier, steering and parallel delegates; cancel owned parent/child work and prevent late dispatch/events. Preserve accepted approvals/questions and unfinished plans/queued messages on graceful close; rebuild original provider/vault/worktree identity after restart. Mark interrupted delegate/activity state truthfully, preserve completed results and never replay uncertain effects. Apply existing redaction before every parent/delegate/summarizer checkpoint, ledger/event and UI payload; canaries in plans, diffs, steering, reasoning and child results must not persist. No inherited tracing, shell secrets or credentials in the workspace. Existing jail race/alias limitations remain documented.
- **R16 — Verification and accessibility.** Add deterministic offline Demo/scripted-provider scenarios for small/big/high-risk plans, deviations, actual parent/delegate activity, partial reasoning, actual summarization and steering. Use real graph/SQLite/processes in recovery/safety tests and real Electron in walkthroughs. Verify keyboard expansion, `aria-expanded`, associated labels/focus, live announcements, logical CSS, fa/en digits, LTR code/paths, reduced motion and narrow layouts. Keep business logic in typed services/stores/hooks. Pass ruff, strict mypy, pytest, strict TypeScript, UI tests, reproducible protocol/OpenUI generation, builds and relevant existing desktop regressions. Record installed APIs, evidence, scope choices/limits and Phase 7 handoff in learnings. Obtain explicit approval of the exact final constitution completion update and commit it with final phase work.

## Draft decisions and scope reconciliation
- Existing constitution/roadmap already assign planning/activity to Phase 6; no constitution edit is needed for this draft. No spec/mock conflict was found. Undrawn threshold/configuration and plan-review states extend existing form/review tokens.
- Concrete-file counting is conservative when globs leave the count unknown. Deviations track stable identities/cumulative additions rather than trusting a replacement todo list. Approval never overrides ordinary tool permissions.
- Workspace planning configuration follows the constitution's `.harness/config.json` layout and its always-ask protection for engine files.
- Run/Main display live context and limits only when real telemetry exists; unavailable values remain explicit while Phase 7 supplies the full budgets/context policy. The reviewer/researcher operate on local workspace context without adding the deferred web backend.

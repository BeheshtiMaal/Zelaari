# Phase 4: Approvals inbox. Requirements

Status: **Approved by the user on 2026-10-19. Implemented; final validation recorded separately.**

## Goal
Turn sensitive actions into durable, reviewable approvals: approve, edit then approve, or reject without crashing the run. Preserve pending decisions across app restarts and never automatically replay an interrupted command.

## In scope
- Durable LangGraph interrupts using the existing asynchronous SQLite saver, approval history, recovery, and concurrent pending decisions.
- Authenticated `GET /approvals` and `POST /runs/{id}/interrupts/{iid}`, generated wire types, and replay-safe events.
- OpenUI ApprovalCard and DiffView; inline approvals, two-pane inbox, sidebar counts and waiting dots.
- Customize hub chrome and Rules grid; explicit approval for rule changes, including the allow-rule checkbox.
- Replace temporary Phase 3 approvals, including branch/worktree flows; localize policy explanations.

## Out of scope
Question tool and QuestionCard (Phase 5), plan gate and timeline (Phase 6), scheduler (Phase 9b), remaining Customize tabs (Phase 8), broad theme/settings polish, packaging. Support source metadata for future schedule approvals and waiting-kind discrimination without inventing schedules, questions, plans or step counts. Giant-directory pagination is outside this phase.

## Functional requirements
- **R1 Durable identity:** persist run reconstruction metadata, graph thread/checkpoint identity, stable approval and interrupt identities, tool-call identity, original inputs, source, timestamps, pending/resolved state, and decisions. Credentials remain in the vault/in memory. Repeated checkpoint announcements or SSE reconnects never duplicate approvals.
- **R2 Concurrent decisions:** every gated call in a model turn has an independent approval. Partial answers persist across restart; execute none of that turn's gated calls until all required interrupts are answered. Resolve each answer to its exact graph interrupt/tool call, never by an ambiguous list position or shared decision. Existing allowed calls must not repeat during resume.
- **R3 Restart:** discover unfinished runs in registered workspaces on engine startup, rebuild pending approvals and history, and restore SSE replay with monotonically increasing event sequences. Closing the app preserves resumable waiting runs rather than converting them into user-stopped runs. Resume with the saved model configuration only once its credential is available; missing model/key/workspace produces an actionable blocked state without discarding approvals. Explicit Stop cancels pending work and cannot execute it later.
- **R4 Crash safety:** durably journal command intent before process launch and completion afterward. An intent without a durable result is treated as interrupted, even if execution might have completed. Recovery never dispatches that call again; show the uncertain outcome and return an interrupted tool result to the model. Any retry is a fresh call requiring a fresh permission decision. Replay of permission nodes must not repeat completed file writes or commands.
- **R5 Approval API:** list pending and historical approvals across registered workspaces/runs with status filtering and source metadata. The decision endpoint supports approve, edit then approve, and reject with optional reason. Validate run/interrupt ownership and schemas; unknown, stale, conflicting and already-resolved submissions cannot execute a call twice. Preserve existing loopback authentication and CORS protections.
- **R6 Edited inputs:** edit tool arguments, not the tool name or call identity. Revalidate the entire edited request through schema validation, jail, current mode, rules and risk classification before execution. A denied edit never runs; a materially changed target/risk requires refreshed review rather than inheriting the original approval. Refresh diff/preview before final confirmation. Reject returns the person's reason as a tool result and the model continues.
- **R7 Accurate review:** supply tool/type, path or command and timeout, risk, source task (or future schedule), time, policy explanation and any actual agent reason. Distinguish policy from agent reasoning; do not invent a reason. Derive file diffs from current contents and proposed operation, with unified hunks, old/new line numbers, addition/removal tints and LTR code. Detect changed underlying contents before applying an approved edit and require a refreshed review. State snapshot/undo availability accurately; retain Phase 3 snapshots and undo.
- **R8 Inbox:** match `Inbox.dc.html`: two panes, 360px list at reference width, selected teal outline, type/title/source/time/risk/available plan metadata, command preview, detailed reason/diff/snapshot note, allow-rule checkbox, rejection textarea and three decision actions. Tabs Pending / Approved / Rejected / All filter real data; recent decisions remain dimmed and inspectable. Resolved rows are read-only. Empty, unavailable workspace and submission errors are usable. Do not hardcode mock data or invent in-plan chips before Phase 6 supplies metadata.
- **R9 Inline OpenUI:** register Zod-defined ApprovalCard and DiffView in the existing library. Render deterministic engine approvals inline with the amber appearance/actions in `Main.dc.html`; support the compact review/open-in-inbox presentation in `Run.dc.html` without implementing its later-phase timeline. Both surfaces share one decision state. Remove the temporary modal and preserve gated branch/worktree actions without approval bypasses.
- **R10 Allow rule:** offer a workspace-scoped tool/path rule such as edit_file on `src/**` only where meaningful. Checking it stages the precise rule change for explicit review; neither checking nor approving the original file action silently writes rules. A linked rule-change approval shows the rules diff and must be approved before an atomic validated save. This satisfies the always-ask rule in Ask and Auto without recursively asking to approve the approval. Rejection leaves rules unchanged. Existing deny/protected-path/high-risk/Read-only boundaries remain authoritative.
- **R11 Rules grid:** rebuild the Customize chrome from `Skills.dc.html`, with Rules and permissions active and later-phase tabs visibly unavailable. Provide workspace selection, effective defaults, tool/path allow/ask/deny rows, add/edit/remove, validation and save status. `PUT /rules` stages an approval instead of immediately saving, replacing the Phase 3 direct-save behavior. Approving the exact reviewed revision writes atomically with a snapshot; stale revisions require refreshed review. Reload effective permissions after resolution.
- **R12 Global indicators:** sidebar badge counts only pending approvals across tasks and future schedule sources. Amber dot marks tasks waiting on any interrupt; resolving one approval does not clear the dot while another decision remains. History, duplicate events and reconnects do not inflate the badge. Reserve question discrimination for Phase 5 without implementing its tool.
- **R13 Interaction and locale:** Persian RTL by default; English via remembered settings. Preserve mock Persian copy, tokens, typography, radii and layout hierarchy. Policy reason codes map to localized messages. Logical CSS only; paths/code LTR; responsive panes, labeled controls and visible focus. Enter approves the active review and Esc rejects outside editable controls; typing in textareas/editors must not trigger a decision. Prevent duplicate submissions and accidental shortcuts on inactive cards.
- **R14 Security and compatibility:** enforce decisions in the engine tool layer, including forged REST requests and edited arguments. No secrets in approval payloads, events, logs, fixtures or persisted state, including SQLite checkpoints and command journals. Preserve existing redaction and address any checkpoint persistence leak before claiming this guarantee. Retain previous phase regressions and document containment limitations honestly.

## Design references and verified starting point
- Read `Inbox.dc.html`, `Main.dc.html`, `Run.dc.html`, `Skills.dc.html` and `docs/design-tokens.md`. Rules inner content is not drawn; use the existing rules schema and shared visual tokens inside the mocked hub chrome.
- `backend/agent/bridge.py` currently holds one `run.pending`/answer in memory and uses `AsyncSqliteSaver`; the persistent inbox and reconstruction do not yet exist.
- `backend/server/rules.py` currently writes directly on PUT. R11 deliberately supersedes this earlier-phase behavior under the explicit Phase 4 always-ask requirement; no constitution change is needed.
- Phase 3 learnings establish approval interruption in `aafter_model` and private permission outcomes; preserve those safety properties. Concurrent and restart behavior must be verified against installed package source before implementation assumptions are finalized.
- Phase 3 timeout retry uses a synthetic task. Replace it with a fresh reviewed command request using explicit arguments and timeout, covered by R4/R6; do not silently replay the old call.

## Non-functional requirements
Typed small Python modules; strict TypeScript; permission/state logic outside components. Every new permission path has real tests. Quality gates: ruff, strict mypy, pytest, TypeScript, UI unit tests, static export and Windows Electron validation. No constitution edits in this draft; roadmap completion changes will be proposed for approval after evidence exists.

## Durable implementation
- `QuestionLedger` writes `.harness/runs/<id>/questions.json` atomically. Accept a complete question-call batch before publishing its answer; independently accepted decisions survive shutdown and reconstruction. Question events contain snapshot copies, so later ledger mutation cannot change an earlier in-memory event.
- Questions and approvals from one model turn share the existing pre-tool interrupt. The mixed resume envelope has separate typed maps; the graph will not enter the tools node until all required calls are resolved. Question answers never override tool permission decisions. Approval-only and configuration-action contracts remain compatible.
- The authenticated run-scoped history endpoint works independently of an active provider session. Missing credentials, changed provider identity and temporarily unavailable workspace leave persisted questions intact. Restoring those dependencies rebuilds the original run; explicit Stop cancels both request kinds.
- Redaction happens in the existing model middleware before checkpointing, again before request/answer ledgers, and before returning question tool results. Canary tests scan actual persisted files, including SQLite. Exact call/run/interrupt identity and stored question validation reject stale, duplicated and forged answers.
- The installed `hook_config(can_jump_to=["model"])` contract is exercised by a real graph test: a prose-only interview finish is redirected to the model for a structured question/readiness transition. Two failed reminders terminate safely instead of pretending readiness. Interview state and the structured summary are checkpoint fields. The existing graph recursion limit remains finite (80 for interviews); this phase does not implement Phase 7's step/time/fix budgets.
- `finish_interview` requires a previously answered batch. A readiness call cannot authorize writes in its own model turn. While interviewing, only safe project reads, questions and readiness are available; commands/delegation/mutations are refused. Declined interviews cannot begin implementation. One question-call batch at a time is exposed in grill mode.
- After readiness, later clarification questions use ordinary declined-answer semantics; declining one does not reopen or cancel the completed interview. The readiness/permission regression also exercises this continuation.

## UI and consumers

A minimal 288px information panel shows only the real pending-request count. Its narrow variant moves above the conversation. No plan, budgets or sub-agent metadata is fabricated.
- Single selects one option or Other; multi permits choices plus Other; rank requires all option IDs in order and permits additional Other text. Ranking has drag/drop and labeled move buttons. Number shortcuts work with physical digit keys in Persian layouts, and include Other when it fits within 1–4. Native text/IME and picker events retain their behavior.
- Back/next preserve drafts; only the final complete batch is submitted. In-memory drafts survive failed submissions; accepted answers survive engine/app restart. Unsubmitted drafts are not represented as accepted decisions. A shared request lock prevents duplicate activation across deterministic/OpenUI views. - Exhaustion uses typed `FailureContext` (actual attempts/step/check/output) and `exhausted_question`, with stable `retry`, `change`, `stop` choice IDs and a separately validated retry hint. The Errors presentation uses its failure badge/output styles and localized actions. Demo consumes real structured results; it does not claim to run an automatic three-attempt correction loop.

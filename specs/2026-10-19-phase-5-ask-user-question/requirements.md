# Phase 5: AskUserQuestion GenUI. Requirements

Status: **Approved by the user on 2026-10-19. Implementation validated; approved roadmap update applied and included with the final phase commit.**

## Goal
The agent can ask structured questions, pause durably, receive identity-bound answers and continue. Users answer in a docked, accessible QuestionCard in the original run. `/grill` interviews the user before implementation.

## Requirements
- **R1 — Validated question schema.** `ask_user_question` accepts 1–3 questions. Each has a stable ID within its call, short nonempty header, nonempty text, `type: single | multi | rank`, and 2–4 options with unique stable IDs, nonempty labels and descriptions. Free-text Other is always available without the model having to add an option. Reject empty/duplicate IDs, invalid types/counts and malformed payloads before publication. Establish explicit bounded string lengths in Step 1 and test boundaries. The tool description instructs the model to read the project first and ask only for information it cannot obtain there; interview preferences may legitimately need the user.
- **R2 — Structured answers.** Results retain run, tool-call, batch and question identity, with `answered` or `declined` status. Single selects exactly one option or nonempty Other. Multi selects at least one option and/or nonempty Other without duplicate IDs. Rank returns every offered option exactly once in user-defined order, plus optional nonempty Other text as an additional preference. Unknown/duplicate/missing IDs and incomplete answered batches are refused. Dismiss declines the whole unanswered tool-call batch and returns a structured `declined` result; it never invents selections. A selected default is not a submitted answer.
- **R3 — One durable barrier.** Extend the Phase 4 pre-tool barrier to collect questions and permission approvals from the same model turn before any sibling tool runs. Each call keeps an independent typed answer; partial decisions persist, and execution resumes only when every required call is answered or declined/resolved. A question answer grants no permission and cannot change a denied/awaiting tool outcome. `ask_user_question` asks for information in all permission modes, including Read-only and Auto, without a second approval card for asking. Existing permission, revision, jail and effect-journal enforcement remains intact.
- **R4 — Authenticated API and events.** Add typed question requests, records, answers and `question.asked`/`question.answered` events to the generated protocol. Support authenticated run-scoped question retrieval and typed resolution through `POST /runs/{id}/interrupts/{iid}` without breaking existing approval clients. Match exact run, graph interrupt and call IDs, validate against the stored request and reject forged, stale, cross-run, duplicate, stopped and already answered submissions without redispatch. No global question inbox is introduced. Define endpoint/error contracts in Step 1 after inspecting existing routes.
- **R5 — Restart and cancellation.** Persist pending requests and accepted answers before announcing them; reconcile publication after crashes. Rebuild the original graph with original provider identity and existing vault rehydration. Graceful quit and force-kill preserve questions and partial mixed decisions; missing keys/workspaces remain recoverable. Explicit Stop cancels pending questions and approvals and prevents later execution. Original calls receive answers once; events stay monotonic and replay reproduces history. Uncertain effect intents are never automatically replayed.
- **R6 — Docked QuestionCard.** Register a Zod-defined OpenUI `QuestionCard` and use the same trusted component for deterministic engine questions. Model-composed controls reference an existing engine-owned question by exact IDs and cannot fabricate an interactive request. Match Main's card above the composer: `#1E2024` surface, 2px `#0E7C86` border, 18px radius, 16px padding, teal header chip, question index, title, stacked options/descriptions, selected teal border/tint, Other and submit footer. Preserve Persian strings including `رویکرد`, `سؤال ۱ از ۱`, `گزینه‌ی دیگر…`, `ارسال پاسخ`; derive indexes and shortcut range from real data. Add English equivalents. No fake reasoning, plan, budget or file metadata.
- **R7 — Batch navigation and selection.** Show one question at a time with real `question X of N`, accessible previous/next navigation and preserved drafts. Submit only a complete batch; intermediate navigation does not resolve the graph. Single uses radio semantics; multi uses checkboxes; rank uses numbered rows/handles with pointer reordering and keyboard-operable move controls. Other selection/text semantics follow R2. Show readable resolved/declined history and disable its controls. Network/schema errors preserve drafts; lock submissions immediately against double activation.
- **R8 — Keyboard/accessibility/RTL.** With focus in an active card and outside editable controls, 1–4 choose/toggle the matching option; for rank they focus the corresponding row and labeled move controls reorder it. Enter advances a valid intermediate question or submits a complete last question; Esc declines that batch. Editing text, IME composition and composer/picker interactions must not accidentally answer or decline. Provide visible focus, associated labels/descriptions, fieldset/legend or equivalent ARIA, announced validation and ordering changes, logical CSS, Persian digits, LTR code/paths and a narrow layout without horizontal overflow. Focus moves predictably on navigation and resolution without stealing focus on polling.
- **R9 — Waiting state.** Questions stay inline in their own run; background tasks can be reopened to answer. Amber task dots cover either questions or approvals. The global badge and approvals inbox count only approvals. Add Main's current-task waiting summary using authoritative pending question-call batches plus approvals (a batch of 1–3 questions counts as one request). Partial answers/decisions update the summary without clearing another waiting kind. Preserve state across navigation, replay and restart; hide the summary when nothing waits. Do not implement the rest of Phase 6's information panel.
- **R10 — Built-in grill interview.** A leading `/grill` selects a persisted interview mode; Home's `مصاحبه با grill-me` chip inserts that command. Start an interview with a user goal or ask for the missing goal. Read available project context, ask one 1–3-question batch at a time and use answers in later batches. Do not invent answers or repeatedly ask an answered question without a stated reason. Before implementation, persist an explicit readiness transition with a concise objective/scope/constraints/acceptance summary; the engine blocks mutating tools and commands during interviewing, while existing safe project reads remain available. Require at least one answered interview batch before readiness. Declining ends the interview without starting implementation; explicit Stop remains available. After readiness, continue the original task through normal permissions, retaining the interview transcript and mode after restart. Verify the installed middleware/tool contract for this transition in Step 1; do not infer readiness merely from prose.
- **R11 — Composer commands.** Typing `/` at the command position opens a localized, keyboard-accessible filtered picker containing `/grill`; arrows navigate, Enter selects and Esc closes without submitting the task or declining a question. Pointer selection inserts the command and keeps the task editable. Plain text and unknown slash text retain normal task behavior without running an unknown command. Reuse existing Home/composer layout and `/`/`@` hints. Other skill commands arrive in Phase 8.
- **R12 — Exhausted-attempts integration.** Provide a reusable engine question constructor and matching Errors presentation for retry with a hint, change approach and stop/report. Bind choices to stable result IDs and include a hint field for retry. Match mock labels `با یک راهنمایی دوباره تلاش کن`, `رویکرد را عوض کن`, `متوقف شو و گزارش بده`; derive failure count, step, failing check and output from supplied engine data. Expose typed results for Phase 7 to consume; never claim automatic budgets or replanning already exist. Fixture-driven execution proves the real interrupt, continuation with choice/hint, and stop/report outcome without reverting approved changes.
- **R13 — Privacy and trusted interactions.** Redact registered secrets from question content, descriptions, Other/hints, results, events, ledgers and checkpoint inputs before persistence, not just from rendered output. Validate canonical IDs after redaction. Asking/answering never runs model-authored UI code or bypasses the workspace jail. Persisted data contains no vault credentials. Test canaries and malformed/forged controls against actual storage.
- **R14 — Verification and handoff.** Add offline Demo scenarios for all question types, mixed waiting, multi-batch grill and exhausted choices. Verify actual SQLite reconstruction and killed-engine recovery, plus real Electron inline interaction, keyboard, command picker and fa/en screenshots. Preserve Phase 4 regression coverage. Pass ruff, strict mypy, pytest, strict TypeScript, UI tests, generated protocol/OpenUI artifacts, static/Electron builds and baseline desktop checks. Record verified package contracts, choices, limits and Phase 6/7/8 handoff in `learnings.md`; obtain explicit approval of the exact final roadmap update before committing it with final phase work.

## Decisions and scope reconciliation
The roadmap already assigns questions and grill-me to Phase 5; no constitution change is needed for this draft. Multi/rank and the slash-picker popup are not drawn in detail, so extend the mocked controls/tokens with accessible native semantics. The mock's three-choice shortcut hint is dynamic when a request contains four options or Other. The exhausted card is implemented as a reusable question consumer now; automatic fix-loop production remains Phase 7 as the constitution specifies.
